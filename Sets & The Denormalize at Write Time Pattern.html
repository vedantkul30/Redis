Sets in Redis: Core Commands, Set Algebra, and the "Denormalize at Write Time" Pattern

High-Level Overview

A set is an unordered collection of unique strings (or numbers, stored as strings) under one key. No duplicates are ever possible — adding an already-present member is a no-op. Core single-set commands: SADD (add), SMEMBERS (list all), SCARD (count), SREM (remove), SISMEMBER/SMISMEMBER (membership test, single/multiple), SSCAN (paginated iteration for large sets). Multi-set "set algebra" commands: SUNION, SINTER, SDIFF (and their *STORE variants, which persist the result under a new key instead of just returning it).

The lecture then builds two real features on top of sets: enforcing unique usernames (a straightforward membership check) and a like system (one set per user of liked item IDs), which surfaces an important, recurring Redis modeling lesson: Redis cannot efficiently answer "how many of my many sets contain this value" — so you precompute and store that count elsewhere instead of scanning all sets on every read.

Why This Concept Exists

Why sets at all? A set gives you two things a plain string or hash can't: automatic deduplication and efficient membership testing (SISMEMBER doesn't need to load the whole collection to answer "is X in here?"). Any time your access pattern is fundamentally "is this value present" or "give me the unique combination of values across a few sources" — rather than "give me an ordered list" or "give me a structured record" — a set is the right tool.

Why union/intersection/difference exist as first-class commands: These are the standard set-algebra operations from mathematics, and Redis computes them server-side, in C, across potentially large collections — which is dramatically faster and more network-efficient than pulling every set's full contents back to your application and computing the union/intersection/difference in application code. This is the same "push the computation to the data" principle behind why databases offer aggregate functions instead of making you SELECT * and sum in your app.

Why *STORE variants exist: Computing a union/intersection/difference over very large sets isn't free — it's proportional to the total size of the input sets. If you need the same computed result repeatedly and the underlying sets don't change every second, it's wasteful to recompute it on every read. SINTERSTORE/SUNIONSTORE/SDIFFSTORE let you compute once and cache the result as a brand-new set, to be read cheaply many times until you decide to recompute it (e.g., on a schedule, or when the underlying sets change).

Why SSCAN exists alongside SMEMBERS: SMEMBERS returns the entire set in one reply. For a set with millions of members, that's a huge single response that could tie up significant memory and bandwidth in one shot. SSCAN trades that convenience for a cursor-based, incremental retrieval pattern — you get one page at a time, at the cost of having to loop until the cursor comes back as 0.

Why the like-count problem forces a denormalization pattern: Redis has no mechanism to run an ad hoc aggregate query across an arbitrary number of independent keys (there's no "count how many of these million sets contain value X" command). If "how many people like this item" were computed by checking every user's like-set at read time, that read would be O(number of users) — completely impractical at scale. The fix is to flip the cost from read-time to write-time: every time a like/unlike actually changes membership, also nudge a precomputed counter (stored as a plain field on the item's hash) up or down by exactly one. Reads then become O(1) — just read the counter — at the cost of a small amount of extra work on every write. This is a specific instance of a very general system-design idea: when a read-time aggregation is too expensive or impossible, maintain the aggregate incrementally at write time instead.

Internal Working

  • Redis sets are implemented internally as either an intset (a compact sorted array, used only when every member is an integer and the set is small) or a full hash table (hashtable encoding) once the set grows past configured thresholds or contains non-integer members. Either way, SADD/SREM/SISMEMBER are O(1) average case per member (hash table) or O(log N) (intset, still very fast for small sets).
  • SADD is O(M) for M members being added in one call; it returns the count of members actually added (i.e., not already present) — not the resulting size of the set.
  • SMEMBERS is O(N) where N is the set's total size — it must return everything, hence the motivation for SSCAN on large sets.
  • SUNION/SINTER/SDIFF are O(sum of all input set sizes) in the general case — SINTER in particular is implemented by iterating the smallest input set and checking membership in the others, which is why intersection is typically the cheapest of the three algebra operations to compute when set sizes are uneven.
  • SDIFF's result is order-dependent on its arguments: it returns members present in the first set but absent from all the others — swapping argument order changes the result. SUNION/SINTER are order-independent (they're mathematically commutative).
  • SSCAN's cursor is not a simple offset/page-number — it encodes an internal iteration position tied to the set's hash-table structure. The guarantee is: every element present for the entire duration of a complete scan (cursor 0 → ... → cursor 0) will be returned at least once, even if the set is concurrently modified during the scan — but elements added/removed mid-scan may or may not appear, and duplicates are possible. This is a weaker but still highly useful guarantee compared to a single atomic SMEMBERS snapshot.
  • SISMEMBER/SMISMEMBER avoid transferring the whole set over the network just to test membership — critical for large sets, since the cost of a membership check stays O(1)/O(M) (M = number of values checked) regardless of how large the set itself is.

Important Concepts

1. The four common use cases for sets

  • Uniqueness enforcement — e.g., a set of all usernames in use; check via SISMEMBER before allowing a new signup.
  • Modeling relationships between records — e.g., one set per user listing the IDs they've liked; SMEMBERS to list them, SCARD to count them, SISMEMBER to check one.
  • Finding common elements across records — e.g., SINTER between two users' like-sets to find mutually liked items.
  • Unordered membership lists where order never matters — e.g., a blocklist of banned email domains, checked purely with SISMEMBER.

2. Set algebra commands and their *STORE counterparts

Command Returns Order-sensitive?
SUNION k1 k2 ... All unique elements across every set No
SINTER k1 k2 ... Elements present in every set No
SDIFF k1 k2 ... Elements in the first set, absent from all others Yes — argument order changes the result
SUNIONSTORE dest k1 k2 ... Same as SUNION, but writes the result to dest instead of returning it inline No
SINTERSTORE dest k1 k2 ... Same as SINTER, persisted to dest No
SDIFFSTORE dest k1 k2 ... Same as SDIFF, persisted to dest Yes

Use *STORE when the same expensive computation will be read repeatedly without the underlying sets changing every request — compute once, read many times, recompute on a schedule or on invalidation.

3. SSCAN vs. SMEMBERS

SMEMBERS is simplest but returns the entire set in one response — fine for small/medium sets, risky for very large ones (memory spike, large single payload, and it can briefly compete with Redis's single command-processing thread on very large sets). SSCAN key cursor [COUNT n] walks the set incrementally: start with cursor 0, keep calling with the returned cursor until it comes back as 0 again, accumulating results page by page.

4. SISMEMBER vs. SMISMEMBER

SISMEMBER key value checks one value, returning 1/0. SMISMEMBER key value1 value2 ... checks several values in a single round trip, returning an array of 1/0 results in the same order as the inputs provided — the set-oriented counterpart to MGET for batching multiple checks into one call.

5. The denormalized-counter pattern (the most important idea in this block)

Because Redis has no way to efficiently aggregate across an unbounded number of independent sets, any time you need a count or aggregate derived from many keys, compute it incrementally at write time and store it as a plain field, not at read time by scanning everything. In the like-system example: adding a user's item ID to their like-set (SADD) is paired with an HINCRBY on that item's hash to bump its likes field, only when SADD reports the value was actually newly inserted (return value 1, not 0) — this guards against double-incrementing on an accidental duplicate request (e.g., a rapid double-click), since SADD is naturally idempotent for values already present.

Practical Examples

  • Uniqueness enforcement: Discord/GitHub-style username or handle uniqueness checks are commonly backed by exactly this pattern — a set of taken usernames, checked with SISMEMBER before allowing signup.
  • Relationship modeling via per-user sets: Twitter/X's "who do I follow" and "who follows me" relationships have historically been modeled with per-user sets in Redis-backed systems for fast membership and count operations.
  • Intersection for mutual connections: LinkedIn's "mutual connections" feature and Facebook's "mutual friends" feature are textbook SINTER use cases — intersect two users' connection sets.
  • Denormalized like/view counters: Reddit-style upvote counts and Instagram-style like counts are universally precomputed and stored as a plain counter field rather than derived by scanning membership sets at read time — for exactly the O(1)-read-vs-O(N)-read reason discussed above.
  • Banned/blocklists: Stripe and other payment platforms maintain blocklists (banned card BINs, banned email domains, banned IP ranges) as sets checked via SISMEMBER/SMISMEMBER during fraud-prevention checks.

Enterprise Java Implementation

Unique username enforcement

@Service
public class UsernameUniquenessService {

    private static final String USERNAMES_SET_KEY = "usernames#unique";

    private final StringRedisTemplate redisTemplate;

    public UsernameUniquenessService(StringRedisTemplate redisTemplate) {
        this.redisTemplate = redisTemplate;
    }

    public boolean isUsernameTaken(String username) {
        return Boolean.TRUE.equals(
                redisTemplate.opsForSet().isMember(USERNAMES_SET_KEY, username));
    }

    public void reserveUsername(String username) {
        redisTemplate.opsForSet().add(USERNAMES_SET_KEY, username);
    }
}

Like system with denormalized counter

@Service
public class LikeService {

    private final StringRedisTemplate redisTemplate;

    public LikeService(StringRedisTemplate redisTemplate) {
        this.redisTemplate = redisTemplate;
    }

    private String userLikesKey(String userId) {
        return "users:likes#" + userId;
    }

    private String itemKey(String itemId) {
        return "items:#" + itemId;
    }

    public void likeItem(String userId, String itemId) {
        Long added = redisTemplate.opsForSet().add(userLikesKey(userId), itemId);
        if (added != null && added > 0) {
            // Only bump the counter if this was a genuinely new like —
            // guards against double-increment on a duplicate/rapid-fire request.
            redisTemplate.opsForHash().increment(itemKey(itemId), "likes", 1);
        }
    }

    public void unlikeItem(String userId, String itemId) {
        Long removed = redisTemplate.opsForSet().remove(userLikesKey(userId), itemId);
        if (removed != null && removed > 0) {
            redisTemplate.opsForHash().increment(itemKey(itemId), "likes", -1);
        }
    }

    public boolean userLikesItem(String userId, String itemId) {
        return Boolean.TRUE.equals(
                redisTemplate.opsForSet().isMember(userLikesKey(userId), itemId));
    }

    public Set<String> likedItemIds(String userId) {
        return redisTemplate.opsForSet().members(userLikesKey(userId));
    }

    public Set<String> mutuallyLikedItemIds(String userIdA, String userIdB) {
        return redisTemplate.opsForSet()
                .intersect(userLikesKey(userIdA), userLikesKey(userIdB));
    }
}

What this does and why:

  • opsForSet().add(...) returns the count of newly added members (mirrors SADD's return value) — checking added > 0 is the direct Java equivalent of the transcript's if (inserted) guard against double-incrementing.
  • opsForSet().intersect(...) maps directly to SINTER, and composes naturally with a follow-up batch fetch (pipelined HGETALLs) exactly like the course's getItems reuse pattern — fetch the intersecting IDs first, then pipeline-fetch the full item records for only those IDs.
  • Reusing a single "fetch many item hashes by ID, pipelined" method for both "user's own liked items" and "mutually liked items" (feeding it the output of SMEMBERS in one case and SINTER in the other) avoids duplicating the pipelining/deserialization logic — the set operation only needs to produce the list of IDs; the batch-hash-fetch logic is identical either way.

Alternative approaches / pitfalls:

  • A common mistake is to compute "how many people like this item" by calling SCARD on some imagined single global set of "likers of item X" — that's actually a perfectly valid alternative model (one set per item, containing user IDs, instead of one set per user containing item IDs) and would make SCARD cheap. The course's chosen model (one set per user) is simpler for the "what do I like" and "what do we both like" queries, but means item-level counts must be denormalized as shown, rather than derived from SCARD directly. This is a good illustration of the query-first methodology: the same like relationship can be modeled in more than one way, and the right choice depends on which queries you need to answer cheaply.
  • Failing to check the SADD/SREM return value before adjusting a denormalized counter is a real production bug source — it silently allows double-counting under retried or duplicate requests (e.g., a client retry after a timeout, or an impatient double-click), and the fix (checking > 0/added) costs nothing extra since the return value is already available.
  • Note (flagged in the lecture, not yet solved): even with the SADD-return-value guard, there remains a subtler concurrency race if two truly independent requests for the same like arrive in overlapping windows — a full fix requires transactions/optimistic locking, covered later in the course.

Architectural Trade-Offs

Approach Advantages Disadvantages Suitable scenarios
One set per user (items they like) Simple "what do I like" and "what do we both like" queries Item-level "how many likes" needs denormalization User-centric like/follow queries
One set per item (users who like it) SCARD gives item-level like count directly "What does this user like" now requires scanning many item-sets Item-centric popularity queries
SMEMBERS for full retrieval Simple, one call Can return a huge payload for very large sets Small-to-medium sets
SSCAN for incremental retrieval Bounded response size per call; safe for huge sets More application code; weaker consistency guarantee during concurrent mutation Very large sets, background/batch processing
Compute intersection/union live (SINTER/SUNION) Always fresh Cost proportional to input set sizes on every read Small/medium sets, or infrequent reads
Precompute via *STORE variant Fast repeated reads Result can go stale until recomputed Expensive computations reused often, tolerant of some staleness
Read-time aggregation across many keys Conceptually simple Not actually supported efficiently by Redis for large key counts Avoid — not a real option at scale
Write-time denormalized counter O(1) reads regardless of scale Slightly more write-side work; must guard against double-counting Any "count across many independent records" need — the standard Redis answer

Complexity Analysis

Command Time Complexity
SADD / SREM O(M) for M members supplied
SISMEMBER O(1)
SMISMEMBER O(M) for M values checked
SCARD O(1) (cardinality is tracked, not recomputed)
SMEMBERS O(N), N = set size
SSCAN O(1) amortized per call (returns a bounded page); O(N) total across a full scan
SUNION / SDIFF O(sum of all input set sizes)
SINTER O(size of smallest input set × number of sets) — cheapest when set sizes are uneven
*STORE variants Same as base operation, plus O(result size) to write the new key

Common Mistakes

Beginner mistakes

  • Using SMEMBERS unconditionally on sets that could grow very large, instead of reaching for SSCAN.
  • Forgetting that SDIFF's result depends on argument order, unlike SUNION/SINTER.
  • Trying to compute an aggregate (like a global like-count) by iterating every user's set at read time.

Intermediate mistakes

  • Not checking SADD's/SREM's return value before adjusting a denormalized counter, allowing double-counting on duplicate/retried requests.
  • Choosing "one set per item" vs. "one set per user" without first checking which queries the query-first methodology actually requires — picking the wrong orientation makes one of your two most common queries expensive.
  • Recomputing an expensive SINTER/SUNION on every single read when a *STORE-and-cache approach would be far cheaper for a slowly-changing input.

Production mistakes

  • Running SMEMBERS on a set that has grown far larger than anticipated in production, causing a large single-response payload and memory/latency spikes — this is the aggregate-collection analog of the KEYS-vs-SCAN mistake seen earlier in the course.
  • Building a like/relationship system without any plan for the read/write race between a duplicate rapid click and the denormalized counter update — acceptable to defer with a comment (as the instructor does), but should be tracked and revisited once transactions are available, not forgotten.

Interview Questions

Basic

  • What guarantee does a Redis set make that a list or hash doesn't?
  • What's the difference between SMEMBERS and SSCAN, and when would you prefer one over the other?

Intermediate

  • Why is SDIFF's result order-dependent while SUNION's and SINTER's are not?
  • Design a like-count feature and explain why deriving the count from set cardinality directly is not viable at scale in the model where each user has their own like-set.

Advanced

  • Compare "one set per user" vs. "one set per item" for modeling a many-to-many like relationship. What queries does each make cheap, and what does each make expensive?
  • Explain the general principle of "denormalize at write time when read-time aggregation is too expensive," and give two more examples of it beyond the like-count case.
  • Walk through the residual race condition in a naive SADD-then-HINCRBY like implementation, even with a return-value guard, and describe at a high level what mechanism would be needed to close it completely.

Senior Engineer Notes

  • The choice of "which side owns the set" (user-owns-items-liked vs. item-owns-users-who-like) is a genuine architectural decision, not a coin flip — always trace it back to which queries you actually need to answer cheaply, exactly as the query-first methodology demands. Revisiting this decision after the data is already in production means a migration, not a code change.
  • Treat "check the mutation command's return value before adjusting a denormalized counter" as a non-negotiable code-review checklist item any time you see an SADD/SREM/similar paired with a counter update — it's cheap to get right and easy to silently get wrong.
  • *STORE variants are worth reaching for the moment a set-algebra computation shows up in a hot read path against inputs that don't change on every request — treat "compute once, cache under a new key, refresh on a schedule or explicit invalidation" as a standard tool, not a special-case optimization.

Key Takeaways

  • A Redis set is an unordered, duplicate-free collection of strings; core operations (SADD, SREM, SISMEMBER, SCARD) are O(1)/O(M) and don't require loading the whole set.
  • SUNION/SINTER/SDIFF compute set algebra server-side; only SDIFF's result depends on argument order. *STORE variants persist the result for cheap repeated reads.
  • Prefer SSCAN over SMEMBERS for very large sets to avoid one enormous single response.
  • Redis cannot efficiently aggregate across an unbounded number of independent sets — any "count across many records" need should be solved by maintaining a denormalized counter at write time (e.g., HINCRBY on a paired hash), not by scanning at read time.
  • Always gate a denormalized-counter update on the underlying SADD/SREM actually having changed set membership (checking the returned count), to avoid double-counting duplicate or retried requests.
  • Modeling a many-to-many relationship as "one set per user" vs. "one set per item" is a real design trade-off — choose based on which queries the query-first methodology says you actually need cheap.
