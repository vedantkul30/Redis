High-Level Overview

This unit is the course's first real "let's build something" moment, and it's built around one core idea: in Redis, you design your data model by starting from your queries, not from your entities. This is presented as the single most important mental model shift in the entire course, so it gets extended treatment below.

Concretely, the lecture walks through:

  1. A design methodology for deciding what to store in Redis and how (data type, size budget, expiration policy, key naming, business logic).
  2. A key naming convention (type:identifier, with a documented variant using # instead of : before a unique identifier, to make a future search feature easier to implement).
  3. A working page-caching feature: cache the rendered HTML of certain routes (about, privacy, sign-in, sign-up) using a plain SET/GET, with a TTL, while deliberately not caching per-user dynamic pages (dashboard, auction detail).
  4. A key-generation helper pattern: centralize key-string construction in one small module/class of functions instead of hand-building strings inline everywhere, to eliminate typo-driven cache-miss bugs.

Why This Concept Exists

Why "queries first, schema second"? In a relational database, you normalize your data into tables based on the entities in your domain (users, items, orders), and the query planner figures out how to satisfy arbitrary queries against that shape at query time. Redis has no query planner. There is no WHERE, no JOIN, no ad-hoc filtering across a large keyspace. Every Redis data structure only supports the specific access patterns its command set provides (get/set a key, scan a set, get a range of a sorted set, etc.). This means if you design your Redis schema the way you'd design a SQL schema — organized around entities — you will very likely end up with a shape that cannot efficiently answer the actual questions your application needs to ask. So the methodology inverts the normal process: enumerate your access patterns first, and only then decide on a data type and key layout that satisfies exactly those patterns and nothing more.

Why cache rendered HTML at all? Server-side rendering (generating a full HTML document per request) is CPU and template-engine work that's identical for identical inputs. If the underlying content doesn't change per-request (a static "About" page) or doesn't change per-user, doing that work over and over for every single request wastes CPU for zero benefit. Storing the fully rendered output as a string in Redis turns "regenerate the page" into "look up a key" — trading a template-render operation for an O(1) in-memory lookup.

Why not cache everything? This is the size-budget half of the methodology, and it's the part beginners skip. Redis holds all of its data in RAM. RAM is finite and comparatively expensive versus disk. A page that's identical for every user (about/privacy/sign-in/sign-up) costs you one copy regardless of how many users you have. A page that's different per user (a personalized dashboard) costs you one copy per user, and that cost scales linearly with your user base — potentially into the hundreds of megabytes or gigabytes for a large product. The lecture's back-of-envelope math (57.1 KB per page × page count × user count) is the exact kind of capacity planning a production engineer needs to do before flipping on a caching layer, not after.

Why a specific key-naming convention? Keys in Redis live in one giant flat namespace — there's no concept of a "table" to scope names within. Without a convention, two different features can accidentally collide on the same key name, or an engineer six months from now can look at a key like sign-in and have no idea what it represents, whether it's safe to delete, or what created it. The type:identifier (or type#identifier) pattern turns key names into self-documenting, colon/pound-delimited paths — similar in spirit to how URL paths or Java package names create a readable hierarchy out of flat strings.

Why centralize key generation in helper functions? Because a key name is a piece of code that has to match exactly everywhere it's used, hand-typing the same string template in multiple files is a classic single-point-of-failure: one typo in one file silently breaks a GET (it just returns nil, not an error) while the corresponding SET elsewhere keeps working fine. Centralizing key construction into one function per key "shape" turns a stringly-typed correctness problem into a compiler-checked function-signature problem.

Internal Working

There's limited new Redis internals here (the underlying commands are the SET/GET you already know), so this section focuses on the operational mechanics of the design process itself and how it maps onto system behavior:

  • Memory/capacity implication of per-user vs. shared caching: shared/static content → O(1) memory relative to user count; per-user dynamic content → O(N) memory relative to user count. This is the single most important arithmetic fact to internalize before caching anything.
  • TTL as a staleness bound, not a correctness mechanism: setting EX 2 (2 seconds, for testing) vs. a much longer production TTL (minutes/hours/days) doesn't make the cached content "correct" at all times — it bounds how long stale content can be served after the underlying source changes. Choosing the TTL is a business decision (how tolerant is this page to being briefly out of date?), not a technical one.
  • Key layout as an access-pattern contract: once you choose page-cache#/about as your key shape, you've implicitly committed to "the route path is the unique identifier for a cached page." Any future feature that needs to look up cached pages by anything other than route (e.g., "invalidate all cached pages created before X") will not be served by this key shape and would need either a redesign or an auxiliary index — a preview of a limitation you'll see recur constantly in Redis modeling.

Important Concepts

1. The Redis Design Methodology (multi-perspective — flagged by the instructor as the most important idea in the course)

Beginner perspective: Don't start by asking "what are my objects?" Start by asking "what am I going to look up, and by what?" Only then pick a data type.

Backend engineer perspective: This is the same discipline as designing a REST API around client needs rather than around your database schema — you're modeling access patterns, not entities.

Distributed systems perspective: Because Redis (in the default single-instance/cluster-key-based model) offers only key-based lookups and a small number of structure-specific query shapes (ranges, set membership, sorted-set ranking), any access pattern not anticipated at design time either requires a full keyspace scan (expensive, and dangerous in production — KEYS */SCAN over a large keyspace competes with your single command-processing thread) or a schema change and data migration.

System design perspective: This methodology is essentially the same principle behind designing DynamoDB or other key-value/wide-column NoSQL schemas: access-pattern-first modeling. If you've worked with DynamoDB single-table design, this will feel very familiar — the two systems arrived at similar design disciplines for similar structural reasons (no ad hoc query engine, need to bake access patterns into key/attribute layout up front).

Production perspective: Getting this wrong doesn't usually blow up immediately — it blows up six months later when product wants a new feature ("show me all cached pages older than a week") that your key layout has no efficient way to answer, forcing either a slow full-keyspace scan in production or a redesign and backfill under time pressure.

2. Deciding what to cache: a size-budget exercise, not a gut call

The lecture's calculation is a template worth reusing on the job:

memory per page × number of distinct cached variants = total cache footprint

For shared/static pages: variants = number of distinct pages.
For per-user pages: variants = number of distinct pages × number of users.

This single distinction is often the deciding factor in whether a page belongs in a full-page cache at all, versus needing a more granular caching strategy (e.g., caching just the expensive sub-components of a personalized page, which isn't covered yet in this course but is the natural next question once you hit this wall).

3. Key naming convention

  • Pattern: {type}:{identifier}, e.g. users:45, items:19.
  • Multiple segments allowed: users:posts:91 to express "posts belonging to a user."
  • This course's variant: replace the colon immediately before a unique identifier with #, e.g. page-cache#/about, reserving : for structural/grouping segments. This is explicitly called out as a non-standard twist done to simplify a future RediSearch-based search feature (not yet covered) — not a general Redis best practice you'd necessarily see elsewhere. Functionally, Redis treats : and # identically; they're just bytes in a string key.

4. Selective caching logic

Only specific routes are cached (about, privacy, sign-in, sign-up) via an explicit allow-list check (if (cacheableRoutes.contains(route))) — dashboards and auction-detail pages are deliberately excluded because they're either per-user or need to reflect near-real-time state (e.g., a hotly contested auction). This is a deliberate, explicit business rule, not something Redis infers for you — Redis has no idea which routes are "cacheable"; that judgment lives entirely in your application code.

5. Centralized key-generation functions

Instead of inline string concatenation ("page-cache#" + route) scattered across the codebase, wrap key construction in a single function (e.g., pageCacheKey(route)) that every read and write path calls. This guarantees the GET and SET sides always agree on the exact key shape, and gives you one place to change the key format later if needed.

Practical Examples

  • Netflix / Hulu marketing pages: Static, high-traffic pages (landing page, help center articles) are prime full-page-cache candidates for exactly the reason given here — identical content per user, so caching cost stays flat regardless of subscriber count.
  • LinkedIn feed vs. LinkedIn "About LinkedIn" page: The feed is deeply per-user and time-sensitive (exactly like the dashboard/auction example) and would need a completely different caching strategy (partial fragment caching, short TTLs, per-user keys) — while a company "About" page behaves like the static routes in this lecture.
  • Stripe's documentation pages: Same content for every visitor, rarely updated — a textbook case for the shared-key, longer-TTL pattern described here.
  • Discord server invite landing pages: Rendered server preview pages are effectively static per server for short windows and are commonly cached with a TTL for exactly the performance reason given in this lecture — avoiding repeated expensive render/lookup work for a page that doesn't change every few seconds.
  • GitHub's repository README rendering: GitHub caches rendered Markdown-to-HTML output because re-parsing and re-rendering Markdown on every single page view for a popular repo would be wasteful — directly analogous to the "don't regenerate HTML you've already generated" motivation here.

Enterprise Java Implementation

The course example uses a SvelteKit (server-side-rendered JavaScript) app; here's the same feature in a Java/Spring Boot server-side rendering context (e.g., Spring MVC with Thymeleaf), which is the realistic enterprise equivalent.

Key generation (centralized, typo-proof)

@Component
public class RedisKeyGenerator {

    private static final String PAGE_CACHE_PREFIX = "page-cache#";

    public String pageCacheKey(String route) {
        return PAGE_CACHE_PREFIX + route;
    }
}

Page cache service

@Service
public class PageCacheService {

    private static final Duration CACHE_TTL = Duration.ofMinutes(30); // production value;
                                                                       // use a short value like 2s only in tests

    private static final Set<String> CACHEABLE_ROUTES = Set.of(
            "/about", "/privacy", "/sign-in", "/sign-up"
    );

    private final StringRedisTemplate redisTemplate;
    private final RedisKeyGenerator keyGenerator;

    public PageCacheService(StringRedisTemplate redisTemplate, RedisKeyGenerator keyGenerator) {
        this.redisTemplate = redisTemplate;
        this.keyGenerator = keyGenerator;
    }

    public Optional<String> getCachedPage(String route) {
        if (!CACHEABLE_ROUTES.contains(route)) {
            return Optional.empty();
        }
        String key = keyGenerator.pageCacheKey(route);
        return Optional.ofNullable(redisTemplate.opsForValue().get(key));
    }

    public void setCachedPage(String route, String renderedHtml) {
        if (!CACHEABLE_ROUTES.contains(route)) {
            return;
        }
        String key = keyGenerator.pageCacheKey(route);
        redisTemplate.opsForValue().set(key, renderedHtml, CACHE_TTL);
    }
}

Usage in a controller

@Controller
public class StaticPageController {

    private final PageCacheService pageCacheService;
    private final TemplateRenderer templateRenderer; // your rendering layer

    public StaticPageController(PageCacheService pageCacheService, TemplateRenderer templateRenderer) {
        this.pageCacheService = pageCacheService;
        this.templateRenderer = templateRenderer;
    }

    @GetMapping("/about")
    public ResponseEntity<String> about() {
        return pageCacheService.getCachedPage("/about")
                .map(html -> ResponseEntity.ok().body(html))
                .orElseGet(() -> {
                    String rendered = templateRenderer.render("about");
                    pageCacheService.setCachedPage("/about", rendered);
                    return ResponseEntity.ok().body(rendered);
                });
    }
}

What this does and why:

  • CACHEABLE_ROUTES is the Java equivalent of the course's cacheRoutes array — an explicit allow-list, checked before touching Redis at all, keeping the "which pages get cached" business decision visible and centralized.
  • RedisKeyGenerator mirrors the course's keys.ts pattern — a single class responsible for producing every key shape used in the app, so a typo can only exist in one place and would be caught immediately (every caller breaks the same way, rather than one caller silently drifting).
  • opsForValue().set(key, value, ttl) uses Spring Data Redis's Duration-based overload, which maps directly onto SET key value EX seconds under the hood via Lettuce.
  • Returning Optional<String> instead of null makes the "nothing cached" case explicit and forces callers to handle it, rather than relying on implicit null-checking discipline.

Alternative approaches / pitfalls:

  • Spring's @Cacheable annotation (Spring Cache abstraction, with a Redis-backed CacheManager) can implement the exact same pattern declaratively: 
    @Cacheable(value = "page-cache", key = "#route", condition = "#cacheableRoutes.contains(#route)")
public String renderPage(String route) { ... }
    This trades explicit control (you write the get/set/TTL logic yourself) for framework convenience (Spring manages the cache-aside pattern for you). The trade-off: @Cacheable is excellent for simple method-result caching, but once your caching logic has nuanced business rules (like the selective route allow-list here, or per-route TTLs), hand-rolled service code like above often ends up clearer and easier to reason about than SpEL conditions on an annotation.
  • Common pitfall: forgetting to set a TTL at all (redisTemplate.opsForValue().set(key, value) with no duration) means the cached page never expires — if the underlying page content changes (a copy edit to the privacy policy), users would see stale content indefinitely until the key is manually deleted or the app is redeployed with a cache-clearing step.
  • Common pitfall: applying this full-page cache pattern to a route that's actually per-user (like a dashboard) without realizing it — because Spring's @Cacheable by default keys only on method arguments, a careless key expression could easily fail to include the current user's identity, causing user A to see user B's cached dashboard. This is exactly the class of mistake the lecture's size/behavior analysis is designed to prevent by making you think about per-user vs. shared content before writing code.

Architectural Trade-Offs

Approach Advantages Disadvantages Suitable scenarios
Cache shared/static rendered pages O(1) memory cost regardless of user count; big win for near-zero effort Only works for content identical across all users Marketing pages, legal pages, docs, sign-in/sign-up shells
Cache per-user rendered pages Fast repeat loads for that specific user Memory cost scales linearly with user count; can blow up your Redis instance's memory budget Small user bases, or content that's expensive to compute but rarely viewed
No caching for dynamic/contested content Always fresh, no staleness risk Full render cost paid on every request Dashboards, live auction pages, anything needing near-real-time accuracy
Hand-rolled cache-aside service code (get/render/set) Full control over TTLs, allow-lists, and edge cases More boilerplate; each route needs explicit wiring Cases with per-route business rules (this lecture's exact scenario)
Spring @Cacheable abstraction Declarative, less boilerplate, consistent pattern across the codebase Less flexible for nuanced conditional logic; easy to misconfigure cache keys Simple, uniform caching needs without complex per-case rules
Inline string key construction Zero setup Highly typo-prone; GET on a mistyped key fails silently (nil), not an error Never recommended past a quick prototype
Centralized key-generator functions/class Single source of truth for key shape; typo becomes a compile-time or immediately-visible runtime issue Slight indirection; must remember to route all key construction through it Any application beyond a toy example — this is the recommended default

Complexity Analysis

Operation Time Complexity Network Overhead Notes
Cache lookup (GET) O(1) 1 round trip Replaces a full template-render, which is comparatively expensive CPU work
Cache write (SET with TTL) O(1) 1 round trip Cost is paid once per unique variant, not once per request
Route allow-list check O(1) (using a Set/hash-set membership check) None — pure in-application logic, no Redis call Always check this before hitting Redis, to avoid a wasted round trip for routes you'll never cache
Memory footprint (shared page) O(P) where P = number of distinct pages — Independent of user count
Memory footprint (per-user page) O(P × U) where U = number of users — This is the number that can spiral out of control and must be sized before committing to the approach

Common Mistakes

Beginner mistakes

  • Designing Redis keys the way you'd design SQL tables (organized by entity) instead of by query/access pattern.
  • Caching a page with no TTL at all, leading to permanently stale content after a content update.
  • Hand-typing key strings inline in multiple files instead of centralizing key construction.

Intermediate mistakes

  • Caching a per-user page as if it were shared content (using a key that doesn't include the user's identity), causing one user to see another user's cached content.
  • Choosing a TTL without thinking about the actual business tolerance for staleness — copying a "2 second" test value into production, or conversely picking an arbitrarily long TTL for content that does change periodically.
  • Not running the size-budget calculation before enabling caching on a page, only to discover in production that memory usage on the Redis instance has grown unexpectedly.

Production mistakes

  • Adding new cacheable routes over time without revisiting the original size-budget math — a page that was cheap to cache as a static page may later be redesigned to include personalized content, silently turning a flat O(P) cache into an O(P × U) one without anyone noticing until memory pressure shows up.
  • Using KEYS pattern* in production to inspect or manage cached keys instead of SCAN — a mistake that isn't unique to this feature but is an extremely common one once teams start accumulating many cache-prefixed keys and want to audit or clear them.

Senior Engineer Notes

  • The "queries first" discipline is worth writing down explicitly as a team convention or an ADR (architecture decision record) the first time you introduce Redis into a codebase — new engineers coming from a SQL background will instinctively try to model entities, and it's much cheaper to correct that instinct in a design review than after a key layout is already in production with real data behind it.
  • Treat the size-budget calculation as a required step, not an optional nicety, any time someone proposes caching per-user content. A five-minute back-of-envelope calculation (page size × user count) has repeatedly saved teams from discovering a memory problem the hard way, during an incident, instead of during design.
  • Centralized key-generation utilities pay for themselves almost immediately and should be a day-one convention on any new Redis-backed service, not something retrofitted later — retrofitting means auditing every existing call site for key-format consistency, which is exactly the class of bug this pattern exists to prevent in the first place.
  • Be deliberate and explicit about TTL choices, and treat "no TTL" as a decision that requires justification, not a default. An un-expiring cache key for content that does occasionally change is one of the most common sources of "why is this user seeing old data" support tickets.

Key Takeaways

  • Redis schema design is query-first: enumerate your access patterns before choosing a data type or key layout — the exact opposite of SQL's normalize-then-query approach.
  • Before caching anything, run the size-budget math: shared/static content costs O(1) relative to user count; per-user content costs O(N) — this single distinction often decides whether full-page caching is even viable.
  • Use a consistent type:identifier key-naming convention (this course uses a # variant before unique identifiers, specifically to support a future search feature) so that keys are self-documenting and collision-free.
  • Centralize key-string construction in one function/class per key shape to eliminate typo-driven bugs — a mistyped key doesn't error, it just silently returns nil on GET, making these bugs unusually hard to spot without this discipline.
  • TTL choice for a cache is a business decision about acceptable staleness, not a Redis technicality — always set one deliberately, and never let a test-environment TTL (like 2 seconds) leak into production by accident.
