High-Level Overview

A hash is Redis's flat key-value structure nested under a single top-level key — think "a JSON object with only string/number values, one level deep, no arrays, no nesting." Core commands: HSET (write), HGET/HGETALL (read one field / all fields), HINCRBY/HINCRBYFLOAT (atomic numeric updates on a field), HSTRLEN, HKEYS, HVALS, HEXISTS, HDEL (delete one field), and plain DEL (delete the whole hash).

The most important content in this unit isn't the commands themselves — it's two client-library gotchas that trip up almost everyone the first time they use hashes from application code (covered under Important Concepts).

Why This Concept Exists

Storing a record (a user, a company, a product) as several separate string keys (user:1:name, user:1:age, ...) works, but means N round trips to read or write N fields, and no natural grouping. A hash gives you one key that groups related fields together, matching the most common real-world need: "store/fetch info about one entity." It's the natural next step up from flat strings once your data has more than one attribute per record — while still avoiding the memory/complexity cost of storing arbitrary nested JSON as a string blob (which you'd have to fully deserialize just to read one field).

Internal Working

  • Small hashes are stored internally as a compact listpack (a memory-efficient flat encoding); once a hash grows past configured thresholds (field count or value size), Redis converts it to a full hash table encoding. Either way, field lookup (HGET) is effectively O(1).
  • HSET key f1 v1 f2 v2 ... is O(N) for N field-value pairs written; returns the count of new fields added (not fields touched) — re-setting an existing field to a new value returns 0 for that field, since it's an update, not an addition.
  • HGETALL is O(N) where N is the number of fields in the hash — it must return everything.
  • HINCRBY/HINCRBYFLOAT are atomic, single-command read-modify-write on one field — same concurrency-safety rationale as INCR on plain strings. If the field doesn't exist yet, it's created starting from 0 before the increment is applied.
  • Over the wire, HGETALL returns a flat array ([key1, val1, key2, val2, ...]), not a nested object — client libraries (Node-Redis, Lettuce, Jedis) reassemble that array into a map/object for you. Worth knowing the raw wire format exists, since not every client or every command does this reassembly automatically.

Important Concepts

1. HGETALL on a non-existent key returns an empty object/map, not null

This is the single most important gotcha in this unit. If you HGETALL a key that was never created, Redis (and most clients) hand you back an empty map — not null, not an error. A naive existence check like if (result) { ... } else { respond 404 } will never trigger the 404 branch, because an empty object is still truthy in most languages. The correct check is to test whether the map has any entries (map.isEmpty() / Object.keys(obj).length === 0), not whether the map itself is falsy.

2. Storing null/undefined-equivalent values breaks client-side serialization

Redis hashes only store strings and numbers. When an application object has a field set to null or undefined (JavaScript) — or more generally, any value the client library can't safely coerce to a string — the client's serialization step can throw, because it tries to call something like .toString() on a value that doesn't support it. The fix is to never hand the client a null/undefined field directly: substitute an explicit sentinel (empty string, or a documented placeholder) and handle its meaning deliberately in your own code, since an empty string and "no value" are not automatically the same thing semantically.

3. Nested objects get silently mangled, not rejected

If a field's value is itself an object (not a string/number), most client libraries won't error — they'll call .toString() on it, which for a plain object typically produces a useless string. Redis hashes are flat by design: don't try to store nested structures directly; flatten them yourself (separate fields, separate keys, or JSON-encode the nested piece as a deliberate string value if you truly need to).

4. HEXISTS checks field existence, not truthiness

HEXISTS key field returns 1 even if the field's stored value is "", "0", or otherwise "falsy" in application terms — it only answers "is this field present in the hash," not "does it hold a meaningful value."

Practical Examples

  • User profile records (Uber driver profile, LinkedIn profile summary): one hash per user (user:#123) holding name, city, rating — the textbook hash use case.
  • Product catalog entries (Amazon/Shopify-style): one hash per SKU holding price, stock count, title — atomic price/stock updates via HINCRBY without touching unrelated fields.
  • Discord user presence/status objects: small per-user hashes updated frequently (status, last-seen) benefit from field-level updates instead of rewriting a whole serialized blob.

Enterprise Java Implementation

@Service
public class CompanyProfileService {

    private final StringRedisTemplate redisTemplate;

    public CompanyProfileService(StringRedisTemplate redisTemplate) {
        this.redisTemplate = redisTemplate;
    }

    public void saveCompany(String id, Map<String, String> fields) {
        // HSET — Spring's HashOperations takes a Map directly, avoiding manual
        // key/value alternation and avoiding the null/undefined pitfall as long
        // as the map never contains a null value (validate before calling this).
        redisTemplate.opsForHash().putAll("company:#" + id, fields);
    }

    public Optional<Map<Object, Object>> getCompany(String id) {
        Map<Object, Object> result = redisTemplate.opsForHash().entries("company:#" + id);
        // Correct existence check: Spring/Lettuce also returns an empty map for a
        // missing key, exactly like the HGETALL gotcha described above — never
        // treat the map itself as the truthiness signal.
        return result.isEmpty() ? Optional.empty() : Optional.of(result);
    }

    public void incrementAge(String id, long amount) {
        redisTemplate.opsForHash().increment("company:#" + id, "age", amount);
    }

    public boolean fieldExists(String id, String field) {
        return redisTemplate.opsForHash().hasKey("company:#" + id, field);
    }

    public void deleteField(String id, String field) {
        redisTemplate.opsForHash().delete("company:#" + id, field);
    }
}

Notes: Java's static typing sidesteps the null/undefined-serialization crash from the transcript — a Map<String, String> simply won't compile with a null value passed carelessly in most idiomatic code paths, but it's still possible to pass a null string deliberately, so validate/sanitize input maps before calling putAll. The empty-map-on-missing-key behavior, however, is identical in Java — this is a Redis/protocol-level behavior, not a JavaScript-specific quirk, so the isEmpty() check above is required regardless of language.

Architectural Trade-Offs

Approach Advantages Disadvantages Suitable scenarios
Separate string keys per field Simple, no gotchas N round trips to read/write a full record; no grouping Very few fields, rarely read together
Hash per entity One key per record; atomic per-field updates; groups related data Flat only — no nested structures/arrays; HGETALL empty-map gotcha Standard "record with a handful of scalar fields" use case (users, products)
JSON string blob per entity Supports arbitrary nesting Must deserialize/reserialize the whole blob to change one field; no atomic single-field update Deeply nested or highly variable-shape data

Complexity Analysis

Command Time Complexity
HSET O(N) for N field-value pairs
HGET O(1)
HGETALL O(N), N = total fields in hash
HINCRBY / HINCRBYFLOAT O(1)
HEXISTS O(1)
HDEL O(1) per field removed
DEL (whole hash) O(N) — must free every field

Common Mistakes

  • Checking if (hashResult) instead of checking for an empty map to detect a missing key.
  • Passing null/undefined fields into a hash-set call without sanitizing them first.
  • Trying to store a nested object or array as a hash field value instead of flattening the data model.
  • Confusing HEXISTS (field presence) with a truthiness check on the field's value.

Interview Questions

  • What does HGETALL return for a key that doesn't exist, and why is that behavior easy to get wrong in application code?
  • Why can't Redis hashes store nested objects or arrays directly?
  • What's the difference between HDEL and plain DEL when working with a hash?

Senior Engineer Notes

  • Always write (or use a library helper for) an explicit "does this hash actually exist" check based on emptiness, never on truthiness — this is a one-line fix that prevents a whole class of silent 404-that-never-fires bugs.
  • Decide up front how your app will represent "no value" for a hash field (empty string vs. a sentinel vs. omitting the field entirely) and apply that convention consistently — Redis won't do this for you.

Connections to Previous Topics

  • HINCRBY/HINCRBYFLOAT reuse the exact atomicity rationale established for INCR/INCRBY on plain strings — same single-threaded, single-round-trip safety argument, just scoped to one field of a hash.
  • The key-naming convention (type#id) from the page-caching lecture applies directly to hash keys (company:#123) — hashes are just another value type living under that same naming discipline.

Key Takeaways

  • A hash is a flat, one-level, string/number-only key-value structure nested under a single Redis key — ideal for "one record, several scalar fields."
  • HGETALL on a missing key returns an empty object/map, not null — always check for emptiness, not truthiness.
  • Client libraries can choke on null/undefined/nested-object field values during serialization — sanitize and flatten before writing.
  • HINCRBY/HINCRBYFLOAT give you the same atomic-update safety for hash fields that INCR gives plain strings.
  • HDEL removes one field; plain DEL removes the entire hash.
