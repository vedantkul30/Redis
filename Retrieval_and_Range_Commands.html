GET, MGET, DEL, GETRANGE, SETRANGE — Retrieval and Range Commands

High-Level Overview

This lecture rounds out the "core string toolkit" with five commands, split into two groups:

Plain retrieval / deletion:

  • GET key — fetch a single value.
  • MGET key1 key2 ... — fetch multiple values in one round trip (read-side counterpart to MSET).
  • DEL key — remove a key and its value entirely, regardless of the data type stored there (works on strings, hashes, sets, lists, everything).

Substring operations:

  • GETRANGE key start end — read a slice of a string value by byte index (inclusive on both ends).
  • SETRANGE key offset value — overwrite part of a string value starting at a byte index, returning the new total length.

On the surface, GETRANGE/SETRANGE look like toy string utilities. Their real value only shows up once you combine them with fixed-width encoding schemes — which you've already seen in the furniture catalog example. This lecture nails down the exact indexing rules, edge cases, and error behavior so you can use them correctly in that kind of design.

Why This Concept Exists

GET/MGET/DEL exist because every data store needs basic read and delete primitives — nothing exotic here. The interesting design decision is MGET: exactly like MSET, it exists to collapse N network round trips into 1. If you need color, model, and year for a product, doing three separate GET calls means three TCP round trips to Redis, each paying network latency even though Redis itself would answer each in microseconds. MGET amortizes that latency cost across all keys in a single request/response cycle. In latency-sensitive systems (page caches, session lookups, product detail pages), this is often the single biggest lever you have before you even reach for pipelining.

GETRANGE/SETRANGE exist because Redis strings are stored as byte arrays, and byte arrays support O(1) random access by offset. If your data has a known, fixed layout — e.g., "byte 0 is furniture type, byte 1 is color, byte 2 is material" — then you don't need to deserialize a whole object, mutate a field, and re-serialize it. You can reach directly into the stored bytes and read or write exactly the slice you care about. This is the same mental model as fixed-width binary record formats in systems programming (think: reading a struct field by byte offset instead of parsing a whole record). Redis just exposes that as a first-class command instead of making you fetch-modify-write the whole string.

Internal Working

GET

  • Redis looks up the key in its main hash table (the keyspace dictionary). If the value's type is not a string, Redis returns a WRONGTYPE error rather than silently coercing it.
  • Time complexity: O(1).

MGET

  • Internally, this is just N independent dictionary lookups executed back-to-back while the server holds the single command-processing thread — but critically, it is one network round trip, not N.
  • For any key that does not exist, or exists but is not a string, MGET returns nil at that position in the response array rather than erroring out the whole command. This is an important behavioral difference from a naive loop of GET calls that might throw per-key — MGET degrades gracefully per-element.
  • Time complexity: O(N) where N is the number of keys requested — still a single round trip, so wall-clock latency is dominated by network overhead once, not N times.

DEL

  • Removes the key from the dictionary and frees the associated value's memory.
  • Works uniformly across all data types (string, hash, set, sorted set, list, stream) because deletion is a keyspace-level operation, not a type-level operation.
  • Time complexity: O(1) per key for simple types, but O(M) where M is the number of elements inside an aggregate type (a very large hash, set, or list) because Redis must free each internal element. This matters operationally: DEL on a truly enormous collection can briefly block the single Redis thread. (This is exactly why UNLINK exists as a non-blocking alternative that reclaims memory on a background thread — worth knowing as an operational fact, even though this lecture doesn't cover it yet.)
  • DEL accepts multiple keys in one call (DEL key1 key2 key3) and returns the count of keys actually removed.

GETRANGE

  • Operates directly on the underlying byte buffer of the string.
  • Indexing is 0-based and inclusive on both start and end. GETRANGE key 0 2 returns bytes at index 0, 1, and 2 — three characters, not two.
  • Negative indices are supported and count from the end of the string (-1 is the last byte), which mirrors Python-style slicing.
  • Out-of-range end indices are clamped to the string's actual length rather than erroring.
  • If the key doesn't exist, Redis treats it as an empty string and returns an empty string.
  • Time complexity: O(N) where N is the length of the returned substring (not the whole string) — Redis doesn't need to scan the full value, just copy out the requested byte range.

SETRANGE

  • Overwrites bytes starting at offset, extending the string if the write goes past the current end.
  • If offset is beyond the current string length, Redis zero-pads the gap with null bytes (\x00) before writing your value — so you can accidentally introduce null bytes into a string if you're not careful about offsets.
  • If the key doesn't exist at all, SETRANGE creates it (zero-padded up to offset, then your value written).
  • Returns the new total length of the string after the write — this is a small but important detail: it's not returning the value, it's returning length, so client code should not mistake the return value for the updated string.
  • Time complexity: O(M) where M is the length of the value being written, plus the cost of any memory reallocation if the string grows.

Memory layout note: Short strings (roughly ≤44 bytes, depending on Redis version) are stored using an embedded encoding (embstr) that's immutable-in-place at the object level; Redis transparently converts to a raw, mutable buffer (raw encoding) once you perform an in-place mutation like SETRANGE or APPEND, or once the string exceeds that threshold. You don't have to manage this yourself, but it explains why SETRANGE on a freshly-SET short string might trigger an internal re-encoding rather than being a truly "free" in-place write every time.

Important Concepts

  • MGET is fault-tolerant per key, not per command. A single missing or wrong-typed key does not fail the whole batch — you get nil in that slot. Your application code must handle sparse results (e.g., iterating and checking for null per position) rather than assuming every position is populated.
  • DEL is type-agnostic. This is a conceptual shift from the string-specific commands you've seen so far — it's your first real signal that Redis's keyspace is a single flat namespace across all data structures, not five separate stores.
  • GETRANGE/SETRANGE indices are byte offsets, not character offsets. For ASCII data (like the single-character encoding scheme from the furniture example) this distinction is invisible. The moment you store UTF-8 text with multi-byte characters, byte offsets and "character positions" diverge, and slicing at the wrong boundary can split a multi-byte character in half, corrupting the string. This is a common production bug source when engineers assume string commands are Unicode-aware — they are not; Redis strings are just bytes.
  • Zero-padding on SETRANGE is a silent behavior, not an error. Writing to an offset far beyond the current length "succeeds" and produces a much larger string full of null bytes. This is worth guarding against in application code (validate offsets against expected schema width) rather than trusting Redis to reject an out-of-bounds write — it won't.

Practical Examples

  • Amazon / e-commerce product catalogs: A product detail page needs title, price, stock, and rating for a single SKU — instead of four GET calls, one MGET fetches all four in one round trip, which matters enormously at Amazon's request volume where shaving one network hop per page view compounds into meaningful latency and infrastructure savings.
  • Netflix personalization rows: Rendering a homepage row of "Continue Watching" requires progress data for 10–20 titles simultaneously. MGET across per-title keys avoids 10–20 sequential round trips before the row can render.
  • Uber driver/rider session lookups: Multiple session attributes (auth token, last known location key, active trip ID) stored under separate keys can be fetched together with MGET when a request needs the full session picture at once.
  • Banking/trading systems and fixed-width ledger encoding: Some high-throughput trading systems use fixed-width binary or character encodings for tick data or order flags (similar in spirit to the furniture example) precisely so that GETRANGE/SETRANGE can update a single flag or field without rewriting an entire record, minimizing both network payload and CPU for high-frequency updates.
  • GitHub/Discord cache invalidation: DEL is the standard mechanism for invalidating a cached page, rendered comment tree, or computed aggregate the moment the underlying data changes — simpler and more explicit than relying purely on TTL expiration when you know exactly which cache entry is now stale.

Enterprise Java Implementation

Using Spring Data Redis (StringRedisTemplate) with Lettuce

@Service
public class ProductCacheService {

    private final StringRedisTemplate redisTemplate;

    public ProductCacheService(StringRedisTemplate redisTemplate) {
        this.redisTemplate = redisTemplate;
    }

    // GET — single value
    public String getProductField(String productId) {
        return redisTemplate.opsForValue().get("product:" + productId);
    }

    // MGET — batch fetch, one round trip
    public List<String> getMultipleProducts(List<String> productIds) {
        List<String> keys = productIds.stream()
                .map(id -> "product:" + id)
                .collect(Collectors.toList());
        return redisTemplate.opsForValue().multiGet(keys);
    }

    // DEL — cache invalidation
    public void invalidateProduct(String productId) {
        redisTemplate.delete("product:" + productId);
    }

    // DEL — bulk invalidation
    public void invalidateProducts(List<String> productIds) {
        List<String> keys = productIds.stream()
                .map(id -> "product:" + id)
                .collect(Collectors.toList());
        redisTemplate.delete(keys);
    }

    // GETRANGE — read a byte slice of an encoded string
    public String getEncodedSlice(String productId, long start, long end) {
        return redisTemplate.opsForValue().get(
                "product:" + productId, start, end);
    }

    // SETRANGE — overwrite part of an encoded string
    public void updateEncodedField(String productId, long offset, String newValue) {
        redisTemplate.opsForValue().set(
                "product:" + productId, newValue, offset);
    }
}

What this does and why:

  • multiGet maps directly onto MGET and is the correct API to reach for whenever you find yourself about to write a for loop calling .get() repeatedly — that loop pattern is a classic beginner performance bug in Spring Redis code.
  • delete(Collection<String> keys) maps to a single DEL key1 key2 ... call, again avoiding a loop of individual deletes.
  • The two-argument and three-argument overloads of opsForValue().get(key, start, end) and .set(key, value, offset) map directly to GETRANGE and SETRANGE respectively — Spring Data Redis exposes these as overloads on the same ValueOperations interface rather than separate named methods, which is easy to miss if you only skim the common single-key get/set methods.

Alternative approaches / pitfalls:

  • Using Jedis directly (jedis.mget(keys), jedis.getrange(key, start, end), jedis.setrange(key, offset, value)) is common in simpler, non-Spring codebases or where you need very tight control over connection pooling, but you give up Spring's declarative connection/transaction management.
  • A common production mistake: calling .get() in a loop over a list of IDs instead of .multiGet(). This works correctly but silently reintroduces the N-round-trip cost MGET exists to eliminate — it's a performance bug, not a correctness bug, which makes it easy to miss in code review.
  • Another common mistake: assuming SETRANGE's return value is the updated string. It is the new length (a Long in the Spring API context, though the fluent set(key, value, offset) overload here returns void — check the exact overload signature you're calling, since Lettuce's raw command does return length).

Architectural Trade-Offs

Approach Advantages Disadvantages Suitable scenarios
Individual GET calls in a loop Simple, obvious code N network round trips; latency scales with key count Prototyping, very low request volume, single-key lookups
MGET One round trip regardless of key count; graceful per-key nil handling All keys must be strings; can't mix in hash/set fetches Fetching related string fields across multiple keys (product fields spread across keys, batch session lookups)
DEL per key Explicit, immediate cache invalidation Requires you to know exactly which keys are stale Precise invalidation after a known write (e.g., product updated)
Relying on TTL expiration instead of DEL No invalidation logic needed Stale data can be served until TTL lapses Data where brief staleness is acceptable (e.g., news headlines cache from the earlier lecture)
GETRANGE/SETRANGE on fixed-width encoded strings Extremely compact storage; O(1)-ish targeted field updates without full deserialize/reserialize Requires rigid, pre-agreed byte layout; brittle to schema changes; not human-readable; UTF-8 unsafe High-volume, fixed-schema data (encoded catalog attributes, flags, compact ledger-style records)
Full string replace via SET for "field update" Simple, no offset math Must reconstruct entire value client-side even to change one field; larger payload over the network Small strings, infrequent updates, no fixed layout

Complexity Analysis

Command Time Complexity Network Overhead Notes
GET O(1) 1 round trip —
MGET O(N) keys, single round trip 1 round trip for N keys Latency ≈ 1 round trip regardless of N (up to payload-size effects)
DEL O(1) per simple key; O(M) per aggregate-type key (M = element count) 1 round trip for however many keys passed Can block on very large collections
GETRANGE O(N) where N = length of returned slice 1 round trip Cheaper than fetching + parsing the whole string client-side
SETRANGE O(M) where M = length of written value (+ possible realloc cost) 1 round trip Zero-padding on out-of-bounds offset adds to the string's new total length

Common Mistakes

Beginner mistakes

  • Looping over GET calls instead of using MGET when fetching several related keys at once.
  • Assuming GETRANGE/SETRANGE indices are character positions in all cases — fine for ASCII, wrong for multi-byte UTF-8.
  • Forgetting SETRANGE's return value is a length, not the updated value, and trying to use it as such.

Intermediate mistakes

  • Using SETRANGE with an offset computed incorrectly (off-by-one in a fixed-width schema), silently corrupting an adjacent encoded field instead of the intended one.
  • Not handling nil entries from MGET — assuming all requested keys will always be present and populated, then hitting a NullPointerException downstream.

Production mistakes

  • Calling DEL on a huge aggregate-type key (a massive hash or set) on the hot path, causing a latency spike across the entire Redis instance because Redis is single-threaded and that deallocation work blocks everything else momentarily. (The correct production-grade fix, UNLINK, is covered later in the course.)
  • Building a fixed-width encoding scheme (like the furniture example) without a version byte or schema migration plan — once you have millions of compact encoded strings in production, changing the byte layout requires a full data migration, not just a code change.

Interview Questions

Basic

  • What's the difference between GET and MGET?
  • What does DEL return, and what happens if the key doesn't exist?

Intermediate

  • Why does MGET return nil for missing keys instead of erroring out the whole call? What design goal does that serve?
  • Explain the indexing semantics of GETRANGE — is the end index inclusive or exclusive? What happens with negative indices?

Advanced

  • What happens internally when you SETRANGE a key at an offset far beyond its current length? What are the memory and correctness implications?
  • Why can DEL cause latency spikes in production, and what alternative command addresses this? (You can reference that UNLINK exists, even though it's covered fully later.)
  • Design a compact string-encoding scheme for a dataset with a small number of enum-like fields (similar to the furniture example), and explain how you'd use GETRANGE/SETRANGE to read and update individual fields. What are the risks of this approach as the schema evolves?

Senior Engineer Notes

  • Treat MGET as your default whenever a code path needs more than one related string key — it's one of the cheapest wins available in Redis-backed systems, and reviewers should flag sequential GET loops in PRs the same way they'd flag an N+1 query in SQL.
  • Fixed-width byte encoding with GETRANGE/SETRANGE is a powerful pattern, but it's also a long-term maintenance liability. Before adopting it in production, ask: will this schema ever need a new field, a wider value range, or Unicode data? If the answer is plausibly yes, consider a hash instead (covered next in the course) — you trade a bit of compactness for a much more forgiving schema evolution story.
  • DEL's blocking behavior on large aggregate types is one of those "invisible until it isn't" production landmines. If you're deleting keys that might hold large collections, treat it the same way you'd treat any potentially expensive operation on a single-threaded system — know your data sizes, or use the non-blocking alternative once you have it in your toolkit.
  • When debugging SETRANGE-related data corruption in production, the first thing to check is always: was this string ever exposed to non-ASCII input? Byte-offset bugs from UTF-8 are a recurring root cause in systems that adopted fixed-width Redis encoding without validating the character set of every field.

Connections to Previous Topics

  • MGET is the direct read-side mirror of MSET, covered in the previous lecture — same motivation (batch multiple keys into one round trip), opposite direction (write vs. read).
  • GETRANGE/SETRANGE are the mechanical commands underlying the furniture catalog encoding example you've already seen (GETRANGE item:1 0 2, SETRANGE item:1 0 "BCD") — that example showed why you'd want this; this lecture nails down exactly how the indexing, padding, and error behavior work.
  • DEL is your first command that behaves identically across every Redis data type — a preview of the fact that hashes, sets, sorted sets, lists, and streams (all coming up) all share the same flat keyspace and the same deletion semantics, even though their internal value encodings are completely different.
  • This continues the running theme from the numeric commands lecture: Redis provides purpose-built commands (MGET, INCR, GETRANGE) instead of making you compose primitives (loop of GETs, GET+parse+SET, fetch-whole-string-then-slice-client-side) precisely because the purpose-built version is faster, and in the INCR case, also correct under concurrency. GETRANGE/SETRANGE don't solve a concurrency problem the way INCR does, but they solve the same class of problem: minimizing round trips and payload size for narrow, targeted operations.

Key Takeaways

  • MGET batches multiple string reads into a single round trip; it returns nil per missing/wrong-typed key rather than failing the whole command — your code must handle sparse results.
  • DEL works across all data types and is O(1) for simple keys but can be O(M) and blocking for large aggregate types — a real production risk on a single-threaded server.
  • GETRANGE and SETRANGE operate on byte offsets, are 0-based, and GETRANGE's end index is inclusive. Negative indices count from the end.
  • SETRANGE silently zero-pads gaps when writing past the current string length, and returns the new total length, not the value.
  • These range commands are only "useful" once paired with a deliberate fixed-width encoding scheme — on their own, applied to arbitrary strings, they offer little benefit and carry real UTF-8 safety risk.
